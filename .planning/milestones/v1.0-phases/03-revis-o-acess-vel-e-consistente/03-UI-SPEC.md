## Spacing Scale

Declared values — **inherited verbatim from `webapp/src/index.css`**, restricted to the standard 8-point
multiples actually in use. Not a new decision for this phase:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding (gap-1, gap-1.5) |
| sm | 8px | Compact element spacing (gap-2, px-2) |
| md | 16px | Default element/section padding (modals use `p-4` = 16px) |
| lg | 24px | Section padding (rare) |

**Correction to the generic GSD 8-point default:** this codebase's declared scale for Phase 3 is
**4 / 8 / 16 / 24** — standard values only. Nothing in the webapp uses 32/48/64, so Phase 3 does not
introduce them either.

**Scope note on 12px (`px-3`) — not a scale value, not touched by this phase:** the existing codebase uses
`px-3` (12px) pervasively for card/section padding and the thumbnail grid gutter. This is a pre-existing,
non-standard rung that predates this contract. Per the checker's rule, a justified exception does not
downgrade a non-standard rung from BLOCK to FLAG, so 12px is **not** listed above as an accepted scale value.
None of REV-01..REV-07 involve spacing or layout (they are keyboard nav, contrast, search-state, border-
radius, date format, button weight, and accent-color scope) — Phase 3 has no spacing work to do and does not
need 12px in its scale. Leave existing `px-3` usages exactly as they are: do not "fix" them to 8/16 as a
drive-by edit, and do not add any new 12px usage this phase. Reconciling the codebase onto a strict
4/8/16/24/32/48/64 scale (if ever done) is Phase 4/CONS-08-adjacent work, out of this phase's scope.

Exceptions: 44px touch targets — not applicable (desktop pointer/keyboard app, no touch surface).

## Typography

Inherited verbatim from `webapp/src/index.css` (`--text-micro`, body via `<html>` `font-size: 13px`,
`--text-realce`). This app has no marketing-style heading/display scale — it is a dense tool UI (Lightroom-
class reference, per `docs/DIRECAO_DE_ARTE.md`).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body (default) | 13px (`--text-corpo`) | 400 (no class = browser default) | not tokenized — leave as browser default this phase; do not add a new line-height rule (see note) |
| Label / secondary | 11px (`--text-micro`) | 400 | not tokenized |
| Panel title (`.titulo-painel`) | 11px, uppercase, `letter-spacing: 0.08em` | 400 | not tokenized |
| Emphasis (filenames, destinations, "Confere", REV-07 de-accented labels) | 13px (inherits body) | **500 (`font-medium`) — canonical for Phase 3 scope** | — |
| Display | not applicable | — | — |

**Emphasis weight — resolved to a single value for this phase.** `font-medium` (500) is the declared,
canonical weight for the Emphasis role in any file Phase 3 actually touches (REV-02, REV-06, REV-07 scope):
`Review.tsx`, `Operations.tsx`, and `TemplateEditor.tsx` use `font-medium` exclusively wherever this role
appears; `Inspector.tsx`'s one `font-semibold` instance (line 38, the file-name header) sits outside the
lines REV-02 touches (lines ~239/246/250) and is left as-is. This is also the value REV-07's own requirement
text specifies: `.planning/REQUIREMENTS.md` REV-07 reads "troca para `font-medium` neutro" for de-accented
labels — the project's own target, not an invented default. Total weights in play for Phase 3: **400 (body)
+ 500 (Emphasis) = 2**, within the dimension's cap.

**Full-codebase reconciliation stays deferred.** The remaining `font-semibold` (600) instances outside
Phase 3's edit scope (`App.tsx`, `Trips.tsx`, `Loupe.tsx`, `Duplicates.tsx`, `Sidebar.tsx`, and
`Inspector.tsx` line 38) are not edited this phase and do not count against this phase's 2-weight
declaration. `docs/AVALIACAO_UX.md` finding B.8 (tokenizing `--font-weight-titulo` project-wide) remains
filed under **CONS-08, Phase 4** — do not attempt that reconciliation here; if a file you're touching for a
different REV item happens to already use `font-semibold` for Emphasis, leave it rather than rewriting it to
`font-medium` as a drive-by (that's Phase 4's job with full-codebase context).

**Line-height:** no project-wide line-height token exists. Do not add one this phase — introducing 1.5/1.2
project-wide is a visual-redesign-scale change this consistency phase does not call for and could reflow
dense rows (thumbnail metadata lines, table rows) in ways nobody has reviewed. Any *new* copy this phase
adds (see Copywriting Contract) should render at the browser default; do not add `leading-*` utilities.

## Color

Inherited verbatim from `webapp/src/index.css`. Values below are the real tokens, not hex approximations of
a 60/30/10 split — this app's surfaces are opacity-modulated over one near-black base (`docs/DIRECAO_DE_ARTE.md`:
"superfícies não têm cor própria"), so the GSD 60/30/10 framing maps onto it as:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-janela` `#08090a` | Window background |
| Secondary (30%) | `--color-painel` `rgba(255,255,255,.02)`, `--color-cartao` `rgba(255,255,255,.05)`, `.superficie` gradient | Panels, sidebar, inspector, cards, sticky group headers |
| Accent (10%) | `--color-acento` `#e8eaee` | See "Accent reserved for" below — this is the one color rule this phase actively enforces (REV-06, REV-07) |
| Destructive | `--color-erro` `#a8615a` | Rejeitar (on hover only, never at rest — see REV-06), error text, destructive hover states |

Other semantic tokens in play this phase: `--color-ok` `#6e9a78` (Aprovar hover), `--color-herdado`
`#6e8fa8`, `--color-atencao` `#c2833a`, `--color-texto` `#fbfbfc`, `--color-texto-2` `#9499a2`,
`--color-texto-3` `#686c73`.

**Accent reserved for** (explicit list, per D-017 and this phase's REV-07):
- Selection (grid/thumbnail outline, active tab underline-equivalent)
- Focus ring (`:focus-visible`, already global in `index.css`)
- Progress / in-flight state (e.g. `CORES_STATUS.executando` in `Operations.tsx` — a status-color map, not
  decoration; classified as **compliant**, not a REV-07 violation)
- Primary CTA fill (`Botao variante="solido"` — background `--color-acento`, text `--color-texto-invertido`)

**REV-07 classification of the borderline cases found during research** (for the planner/executor, not a new
audit — do not re-derive this):
- `TemplateEditor.tsx` — already uses `font-medium`/`text-texto-3`, not `text-acento`. The original 2026-08-06
  finding (B.5, line 139) appears already resolved. Verify before touching; do not "fix" what isn't broken.
- `Operations.tsx` `CORES_STATUS.executando: "text-acento"` — **compliant**, this is per-status semantic
  color-coding (progress state), not a persistent decorative label.
- `LinhaDoTempo.tsx` active-month styling, `Duplicates.tsx` active-filter styling — **compliant**, these are
  "currently selected value in a segmented control," which is Selection, one of the four reserved uses.
- `RetomarScan.tsx:57`, `StatusBar.tsx:135` (`border-acento text-acento` on a button, at rest, not just on
  hover) — this is the real violation pattern (persistent colored CTA), but it is filed as **CONS-03,
  Phase 4** ("Retomar"/"Gerar sugestões" migram para contorno neutro+hover), not REV-07. Do not fix in
  Phase 3; flag for Phase 4 if touched incidentally.

## Interaction Contract (Phase 3 specific)

Not part of the standard template, added because this phase is interaction-first (accessibility), not
visual-first.

**REV-01 keyboard pattern (for any collapsible/expandable header, not just Review's group header):**
```
role="button"
tabIndex={0}
aria-expanded={aberto}
onKeyDown={(e) => {
  if (e.target !== e.currentTarget) return;  // let inner buttons handle their own Enter
  if (e.key === "Enter" || e.key === " ") { e.preventDefault(); alternar(); }
}}
```
This exact pattern already exists in `Review.tsx` (group header, lines ~173-188) — **treat it as already
satisfied for Review, and as the template to replicate anywhere else in this phase's scope that has an
`onClick`-only expand/collapse affordance** (verify `Inspector.tsx`'s "Metadados do arquivo" disclosure,
which already uses a native `<button>` and is therefore compliant by construction; native `<button>` needs
no extra `role`/`tabIndex`).

**REV-06 exact class contract** (single weight for Aprovar/Rejeitar in both header and row context):
- Aprovar: `bg-transparent text-texto-2 hover:border-ok hover:text-ok` (neutral at rest, `--color-ok` only on
  hover/focus)
- Rejeitar: `bg-transparent text-texto-2 hover:border-erro hover:text-erro` (neutral at rest, `--color-erro`
  only on hover/focus)
- This already matches both `Review.tsx`'s group-header "Aprovar N" button and the per-row Aprovar/Rejeitar
  buttons as of this research pass — the B.4 finding (cabeçalho neutro vs. linha colorida em repouso)
  appears already resolved. Confirm class strings match exactly (including `border` being present via the
  `Botao` `contorno` fallback, not just text color) before marking REV-06 done; do not introduce a third
  variant.

**REV-02 (`texto-3` as content text) — where the violation genuinely still exists**, based on this research
pass (do not re-audit from scratch, start from this list):
- `Inspector.tsx`: "Este arquivo não trouxe metadado nenhum." (line ~239), namespace labels (`ns.rotulo`,
  line ~246), metadata keys (`item.chave`, line ~250) — these convey real content, not decoration; promote
  to `text-texto-2`.
- `Operations.tsx`: `CORES_STATUS[...] ?? "text-texto-3"` fallback (used when a status string isn't in the
  known map, lines ~153, ~223, ~291) — an unrecognized status is still content the user needs to read;
  fallback should be `text-texto-2`, not `text-texto-3`.
- Elsewhere, `text-texto-3` used for counts/timestamps/captions in parentheses (e.g. `(data.total)`,
  "classificado por você") is decorative/secondary by design and should **not** be changed — don't
  over-apply REV-02 to every `text-texto-3` occurrence in the codebase.

**Discrepancy note for the planner (report, not resolved further here):** cross-checking REQUIREMENTS.md
(REV-01 through REV-07, all listed `[ ]` pending) against the current code state found that REV-01
(keyboard-navigable header), REV-04 (`rounded-md` in modals — no `rounded-lg` anywhere in `webapp/src/`),
and REV-05 (`formatarData()` already used in `Inspector.tsx` line 42) appear **already implemented**,
mirroring how BUG-01/02/04 turned out to be pre-corrected in Phase 2. This is evidence from a single research
pass, not a verification pass — the planner/executor should confirm with tests/visual check before marking
these done, but should not assume REQUIREMENTS.md's "pending" status is current without checking.
